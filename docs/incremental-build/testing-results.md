### Comparison to Full Build

The full cloudflare-docs build (all 6,080 pages rendered) takes significantly longer in the rendering phase. The incremental build reduces rendering from the dominant cost to a negligible one. The Vite bundling phase (~106s) is now the bottleneck and is unchanged between full and incremental builds.

## What Triggers Full Rebuild (Phase 1 Conservative Rules)

| Trigger                                         | Verified                               |
| ----------------------------------------------- | -------------------------------------- |
| Change to `astro.config.*` or `package.json`    | Yes (via globalFiles check)            |
| Change to any non-content source file in `src/` | Yes (component manifest diff)          |
| Change to any partial (`src/content/partials/`) | Yes (non-docs collection change)       |
| Change to any data collection entry             | Yes (non-docs collection change)       |
| Missing or corrupted `dist-meta/` directory     | Yes (early return → full rebuild)      |
| First build (no `--previous-dist`)              | Yes (normal build, metadata persisted) |

---

## Observations

1. **Content sync "Astro config changed"**: On the first run after adding the `incrementalBuild` Zod schema field, the content layer detected a config change and cleared/rebuilt the entire data store. Subsequent runs skip this since the config stabilizes. The digest comparison still works correctly because content file digests are deterministic.

2. **Vite re-optimization**: Every build shows "Re-optimizing dependencies because vite config has changed" — this is a Vite-level cache invalidation unrelated to our incremental build. It adds overhead to each build.

3. **The `_astro/` directory**: CSS/JS chunk hashes from the incremental build are identical to the full build because the Vite prerender environment still bundles ALL routes. Only the HTML rendering is filtered. This is correct behavior — chunk content-hashing ensures consistency.

4. **Non-docs routes** (e.g., `src/pages/index.astro`, `404.astro`, RSS feeds): These are generated by the normal build pipeline (not filtered by our prerenderer wrapper since they have static pathnames, not dynamic `[...slug]` params). They are always regenerated by the build and are NOT overwritten by `copyCleanPages` (which checks `fs.existsSync` before copying).

5. **Data store size**: The `data-store.json` is ~36 MB (devalue-serialized). Loading, parsing, and diffing two copies takes ~4 seconds. This is acceptable but could be optimized in the future (e.g., streaming comparison, or persisting a smaller digest-only manifest).

# Phase 3 Testing Results (Skip Vite Build)

**Date**: 2026-03-21

## What Changed

When `computeDirtyPathnames()` returns non-null (content-only changes detected, no source file changes), the entire Vite bundling phase (~106s) is skipped. Instead:

1. BuildInternals is restored from `dist-meta/build-internals.json`
2. Prerender bundle + client chunks are copied from `dist-meta/.prerender/` and `previousDist/_astro/`
3. `ssrMoveAssets()` and `generatePages()` run directly with the restored internals
